# ECS 架构

## 唯一权威状态

ECS World 中的实体、组件和 Buffer 保存全部玩法状态。应用入口解析地图根后，将 EntityManager、根实体和会话生命周期显式交给 UI 与表现服务；面板不自行查找默认 World 或推断当前根。Session 是阶段根；建筑、士兵、英雄、任务、远征、人才和王室成员使用持久身份。SO 只编辑模板，不在运行时保存王朝状态。

```text
22 类领域 DefinitionAsset / 各域 CatalogAsset / MapAsset / 独立 Settings Authoring
                              ↓ 各域 Compiler / Baker
          各域 Catalog Blob / typed Prefab Buffer / 初始组件
                              ↓
UI 输入 → 具名 IGameRequest → 队列元数据 + 独立载荷实体 → 领域执行 → ECS 状态 → UGUI / TMP / 外观
                              ↓
                     白天保存 / 白天与黄昏节点
```

程序集按依赖方向拆分，运行层不反向引用界面或应用入口：

| 程序集 | 脚本目录 | 职责 |
| --- | --- | --- |
| Landsong.ECS | Scripts/ECS/Simulation、Persistence | 运行数据、模拟、事务与存档；直接适配 A* Pro 导航和 ES3 持久化，不引用 Authoring、UI、Application、Presentation 或 Moyo |
| Landsong.Content.Runtime | Scripts/Content | 显示 DTO、生成目录、建筑预览槽和选择规则；仅依赖 Core 与运行 API |
| Landsong.ECS.Authoring | Scripts/ECS/Authoring | 配置资产、校验、Baking 和 Entities Graphics 接入；依赖运行核心 |
| Landsong.ECS.AI | Scripts/ECS/AI | Behavior Designer 决策适配及其与核心战斗组的执行边界；依赖运行核心 |
| Landsong.ECS.Presentation | Scripts/Presentation | UI 使用的接口与数据服务、设置、声音、文本和世界表现；不引用具体面板 |
| Landsong.Animation | Scripts/Animation | 消费核心动画信号，向 Rukhanka 控制器传参及烘焙士兵模型；骨骼动画由插件执行 |
| Landsong.Animation.Preview | Scripts/AnimationPreview | 独立动画预览，仅编辑器/Development 编译；不创建正式会话 |
| Landsong.UI | Scripts/UI | Moyo 根面板和领域子视图；通过接口请求应用行为 |
| Landsong.Application | Scripts/Application | 创建持久根，串行切图、恢复、打开/释放会话面板及显式绑定 |
| Landsong.Verification | Scripts/Verification | 编辑器/Development 完整流程验证；Release 不包含 smoke 行为 |
| Landsong.ECS.Editor | Scripts/ECS/Editor | 原生 ECS 配置与制作入口 |

Moyo.Runtime 独立于项目业务。项目级地图、美术和验证工具保留在 Scripts/Editor 的默认编辑器程序集中；不靠挪入默认运行程序集绕过依赖关系。不要为了“全 ECS”把 Canvas、Camera、AudioSource 等展示接口强行变成玩法数据。

模拟和持久化保留在同一运行核心中：经济预演、入夜确认使用完整候选状态和恢复事务，持久化也需要运行规则进行合法性校验与重建。建筑视觉槽等只读运行数据归入 Simulation/Contracts；Hybrid、Graphics、Opsive 和 Rukhanka 适配不进入核心。DBP 适配在决策后、核心战斗组前执行；A* Pro 和 ES3 是核心的明确基础设施依赖。

UI、Presentation、Application 不引用 Authoring。各域 DisplayCatalogCompiler 从对应 CatalogAsset 单向生成说明、图标及布局，UI 显式引用所需领域的显示目录，构建校验拒绝过期输出。静态建筑和动画角色的正式模型都由内容定义引用的 ECS Prefab 拥有，玩法规则来自各域烘焙 Blob。

## 时序与职责

- GameLoopSystem 只编排初始化、请求消费、夜晚推进和历史裁剪。每种操作实现独立的 IGameRequest 载荷；QueuedGameplayRequest 仅保存顺序、路由、来源名称和载荷 Entity。GameplayRequestProcessing 消费队列，GameRequestExecution 校验阶段、暂停、情报和许可门禁后交给领域服务；请求完成后释放载荷实体。请求队列不写入存档。
- 经济按稳定建筑 ID 逐栋提交，前一栋产出可以用于后一栋当次加工。不能因为合批方便改变资源竞争顺序。
- 夜间感知、战术选择、攻击生成、飞行物和伤害由 Landsong ECS 系统执行；导航图适配、ABPath 搜索和 ECS RVO 避让由 A* Pro 执行，最终位移仍投影回权威分层地表。
- DBP 编辑源烘焙为 Entity Task，选择休眠、撤退、玩家命令、攻击或巡逻意图。它不直接扣库存、扣生命、发奖励或保存。
- CheckpointSystem 消费存取请求；SimulationLifetimeSystem 清理失去根所有者的运行实体。
- InventoryTransaction 负责库存、待存放及本次追加的经济账本/历史回滚；奖励事务额外覆盖许可、研究行、Session、事件、战报、夜间提交标志和完整历史行，包含消息合并对已有历史行的修改。奖励事务不创建/销毁实体或执行外部 I/O；采集、招募、英雄出场等实体操作仍由各自领域事务保护，不能只恢复资源数值。
- GameEvent 携带 HistoryCategory，手动库存操作携带命令种类。历史筛选不从中文消息内容反推业务类别；名称和文案仅用于展示。

## 许可、奖励与效果

建筑蓝图、永久增益、功能许可、任务完成、远征完成和科技进度分别保存为 `BlueprintUnlock`、`OwnedBuff`、`UnlockedFeature`、`ClaimedQuest`、`CompletedExpedition`、`TechnologyProgress`。各记录持有本领域 ID；没有统一 Entitlement 表，也没有可混用的内容整数索引。建筑蓝图取最高许可等级，Buff 许可不等于临时实例或叠层，功能许可仅一级；`limit.*` 已成为独立 BuildingLimitGroup，不能作为功能许可发放。恢复直接导入领域事实，不重放奖励。

`RewardDelivery` 预检具名的 DefinitionRewards，再由奖励事务提交物品、蓝图、增益和功能许可。奖励保持物品先、许可后，各次遍历按 Order 稳定排序；同一批新增增益不反过来影响已结算物品。普通完整奖励无法存放时整批拒绝，夜间可进入待存放；人才回合物品仍按可容纳数量存放。任务/远征完成标记与奖励在同一提交边界。研究点、排队顺序和完成次数由 TechnologyProgress 保存。

效果计算分成 `ItemEffects`、`BuildingStatEffects`、`SoldierEffects`、`HeroEffects`、`KingdomEffects`、`IntelligenceEffects` 和 `PersonalRiskEffects`。内部 EffectContributions 只枚举效果来源，目标匹配与计算属于各领域服务；说明与数值使用相同匹配规则，不创建第二份效果状态。EffectAuthoringBoundary 明确拒绝没有执行者的效果。人才被动岗位效果与周期收益是独立结构；受益对象和数量缩放来源分别使用强类型字段。建筑范围效果保留原叠加规则，当夜士兵、英雄和建筑防御分别使用 PreparedSoldier、PreparedHero、PreparedBuildingDefense 冻结。

ECS、命令调度、恢复事务和 AI 边界保持单一权威；具体来源与扩展约束见 [定义系统](定义系统.md)，本轮实际结果见 [当前修复与验收记录](ECS/问题修复记录20260917.md)。

## 表现与制作

Entities Graphics 负责烘焙的静态模型。建筑定义直接引用带模型的完整 ECS Prefab；需要骨骼动画的角色由自己的 ECS Prefab 引用 Rukhanka View Prefab，并按出勤状态创建或释放 View。WorldPresentationView 只为尚未迁移的旧角色提供临时外部模型，不再接收新角色映射；特效使用 PresentationEffect 模板。Animator、Renderer、粒子和灯光均在编辑器显式配置，不在运行时扫描或补组件。

带 `AnimatedUnitVisual` 的士兵由 `Landsong.Animation` 与 Rukhanka 负责，WorldPresentationView 跳过这些实体的模型创建。持久逻辑预制体与动画表现预制体独立：出勤时创建表现，以 Parent 跟随逻辑根，归营或死亡展示结束后销毁表现自己的 LinkedEntityGroup。逻辑根仍负责移动、导航与 DBP 决策；Rig 关闭 Root Motion，消费速度、攻击、有效受伤和死亡状态。动画信号、实例引用与播放进度不写入玩法快照；适配器清理失去逻辑实体的表现，并通过同会话 SimulationOwner 参与切图清理。核心不引用 Rukhanka。当前接入和制作入口见 [罗马士兵动画](昼夜与战斗系统/罗马士兵动画接入.md)。

AudioRuntime 只消费 AudioCatalog，使用持久 UI 根已配置的固定音源池，不拥有王朝状态、不创建 AudioListener。应用流程显式绑定/解除它与 WorldPresentationView 的会话；世界表现根模板实例移入明确的 Game 场景，并在解除会话时清理。LocalizationRuntime 独立消费 LocalizationCatalog；世界视图直接绑定 WorldVisualCatalog 与 EffectCatalog，肖像视图绑定 PortraitDisplayCatalog，夜晚 HUD 绑定 NightCaptionDefinition，不再存在统一表现目录。应用设置通过 ES3 PlayerPrefs 后端独立保存。动画和 Transform 不反向决定伤害、移动或奖励。

## 身份与恢复

内容编辑使用稳定字符串 ID，各领域运行 ID 包装本目录索引；v33 存档编码该领域索引，并以 ContentFingerprint 绑定全部目录的稳定 ID、顺序和玩法内容。个体使用 ulong Identity.Id。Entity 句柄只在当前 World 有效，不能直接持久化。动态实体必须具有 SimulationOwner。

载入先校验全部节点和内容签名，再在同步恢复事务内创建候选实体、恢复稳定 ID 关联并提交。提交前保留原实体，失败恢复原状态。新可变根组件或 Buffer 必须登记 RestoreTransaction.RootState；未登记的 Landsong 根类型在候选构建前拒绝恢复，只读配置使用明确白名单，不能借白名单掩盖可变状态。

所有权清理与应用释放审计包含 Disabled 运行实体，仍存活的 Disabled Session 在同步恢复期间是合法 owner。入夜前的失效任务容器协调在候选事务中执行，扣罚和任务销毁不先写入正式白天；取消或失败只保留必要的确认信息。

当前快照 v33 由 SnapshotBinary 分领域 partial 文件显式逐字段编码，并以字段覆盖检查阻止新增字段静默遗漏；王朝封装 v4 由 ES3 序列化、Gzip 压缩并通过 ES3 文件 API 持久化和备份。开发期间不维护旧存档兼容层，非当前版本直接拒绝。

夜晚不能保存逐帧战斗。回退节点表示重新进行该夜，不承诺物理、渲染或多线程逐帧回放一致。

## 定义与世界组合

ECS 不要求所有系统共用一个定义。当前以 22 个独立领域契约替代 GameDefinitionAsset、GameCatalogAsset、ContentKind、ContentSource、ContentDefinition、Rule 和 Sim 通用入口；各领域资产、编译器、Blob、ID、查询与预制体映射各自拥有边界。跨域引用通过指定目录的 typed index 解析，未注册的同名资产也会被拒绝。没有全目录扫描解析器。

`GameContentSet.asset` 是制作时唯一的领域目录组合源，`GameWorldTemplate.prefab` 只挂一个 `GameContentSetAuthoring` 并引用它一次。各域保留独立的 `XxxCatalogBaker`、编译器、Blob 和强类型缓冲区，不再挂载 `XxxCatalogAuthoring` MonoBehaviour；中央内容集只消除重复的制作入口，不成为运行时万能容器。每个 Baking World 和正式游戏 World 都获得自己的烘焙数据，不共享可变世界状态。

`GameWorldTemplateAuthoring` 只创建与地图无关的模拟根状态和缓冲区。`GameWorldMapAuthoring` 只存在于地图生成子场景，负责 MapAsset、王朝名称、基础人口、随机种子、初始建筑和网格。地图烘焙先实例化公共模板，再添加当前地图的 `GameWorldMapAuthoring`；因此模板不需要预先知道任何具体地图。Session 只保存阶段及初始化标志，其余根状态按职责分组件。建筑功能作为 BuildingDefinition 的具名 Capabilities 保存；建筑实例状态也按生产、库存、人口、驻军等职责分离。

定义迁移保留 185 个正式资产的 GUID、值和领域内注册顺序，以及 408 个跨域引用；29 个 limit.* 资产保留 GUID 后归入 BuildingLimitGroup，4 个实际功能许可继续归入 Feature。PolicyGroup 目录当前为空。任务目标使用稳定 Key，奖励与随机敏感数组保持显式 Order。新增定义和功能的操作路径见 [定义系统](定义系统.md)。这些内容对照不代表旧存档兼容；快照 v33 会拒绝旧版本，需新建王朝。
