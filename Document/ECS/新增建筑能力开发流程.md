# 新增建筑能力开发流程

先判断需求是否已由 `BuildingCapabilitiesSource` 的具名模块支持。新增一座科研建筑只需按 [建筑制作流程](建筑玩法与制作工作流.md) 启用 Research 并配置等级数据；不增加建筑 ID 分支。只有新增运行语义时才修改下面的代码链。

## 可运行的参考：每回合科研产出

在创建器产生的新建筑中配置 `Capabilities.Research.Enabled=true`，`Levels` 中添加 `Level=1`、`PointsPerTurn=3`。建筑运营后，白天正常结算为根的 `ResearchState.Points` 增加科研点。它没有独立进度，也不需要新增玩家命令。

| 职责 | 当前文件（均相对 `Assets/Landsong/Scripts/`） | 需要观察的实际内容 |
| --- | --- | --- |
| 作者字段 | ECS/Authoring/Definitions/Buildings/BuildingResearchSource.cs、BuildingResearchLevelSource.cs | Enabled、Levels、Level、PointsPerTurn，中文标签及禁用时隐藏 |
| 编译 | 同目录 BuildingResearchCompiler.cs、BuildingResearchLevelCompiler.cs、BuildingCapabilitiesCompiler.cs | 禁用模块输出空数组；把作者字段写入强类型记录；非法值由领域校验拒绝 |
| 运行定义 | ECS/Simulation/Definitions/Buildings/BuildingResearch.cs、BuildingResearchLevel.cs、BuildingCapabilities.cs | 只读 Blob 数据，不保存 Unity 对象 |
| 消费时机 | ECS/Simulation/Economy/DailyEconomySettlement.cs、BuildingProductionSettlement.cs | 按稳定建筑顺序结算，只消费当前等级/通用等级的科研记录 |
| 状态和研究 | ECS/Simulation/State/ResearchState.cs、ECS/Simulation/ResearchOperations.cs | 根科研点与研究队列；研究进度为 TechnologyProgress |
| 内容签名 | ECS/Persistence/Serialization/DefinitionFingerprint.Fields3.cs | Research/Level/PointsPerTurn 显式进入内容签名 |
| 行为与恢复 | Editor/Tests/Verification/TechnologyVerification.cs、ResearchAuthorityVerification.cs、PersistenceContractVerification.cs | 入队、扣点、奖励事务、字段覆盖、快照恢复 |

上述模块说明现有能力如何贯穿代码，不是把未来功能放入科研类的模板。新增被动能力应有自己的具名 Source、运行定义和消费服务。

## 新能力逐文件操作表

以下以 `Treatment` 作为示意名称；项目未新增治疗玩法。目录与挂接点为当前实现。

| 顺序 | 文件与职责 | 必须完成的改动 |
| --- | --- | --- |
| 1 | ECS/Authoring/Definitions/Buildings/BuildingTreatmentSource.cs（新建） | 明确 Enabled、条件、资源引用、等级记录；中文 Inspector、必需引用 Required、禁用字段 ShowIf。引用用具体领域资产 |
| 2 | ECS/Simulation/Definitions/Buildings/BuildingTreatment.cs（新建） | 定义运行需要的标量、强类型 ID 和 BlobArray，不保存 SO、GameObject 或通用参数袋 |
| 3 | BuildingTreatmentCompiler.cs（新建）、BuildingCapabilitiesSource.cs、BuildingCapabilitiesCompiler.cs、运行 BuildingCapabilities.cs | 加具名字段；编译合法值，禁用时输出空结构；拒绝非法值、未注册引用和不支持的组合 |
| 4 | BuildingCatalogBaking.cs、BuildingCatalogCompiler.cs | 新增跨域引用时补对应索引参数和 DependsOn，不扫描全项目推断引用 |
| 5 | ECS/Simulation/Buildings/ 下的独立服务（新建），以及真实触发阶段 | 实现实际消费者，规定执行顺序、资格、资源竞争和失败结果。每回合能力接入 DailyEconomySettlement 的适当阶段；事件能力接入对应事件链 |
| 6 | Buildings/State/、BuildingCreation.cs、BuildingLevelConfiguration.cs | 只有需要可变状态或派生属性时才加组件；同步创建、升级、荒废/修复及销毁的生命周期 |
| 7 | Buildings/BuildingRequests.cs、Requests/BuildingRequestDispatch.cs、BuildingCommandHandler.cs、Components.cs 的 CommandKind | 有玩家操作才新增独立 IGameRequest；补类型路由、阶段/许可门禁和共享报价。界面使用 GameplayRequests.Enqueue，不直接改状态 |
| 8 | UI/GamePanel/UI_GamePanel_BuildingDetails.cs 及独立子视图，Editor/DisplayCatalogs/BuildingDisplayCatalogCompiler.cs | 界面读取权威状态、显示报价并发请求；静态显示字段按需加入显示目录 |
| 9 | ECS/Persistence/Serialization/DefinitionFingerprint.Fields*.cs | 所有影响玩法的定义字段纳入显式签名；图标和布局等纯显示内容保持现有边界 |
| 10 | Persistence/Snapshots/BuildingSnapshot.cs、BuildingStateValidation.cs、Serialization/SnapshotBinary.Fields*.cs | 新持久状态同步 Capture、Write、Read、Restore 和合法性；纯派生状态不写入。协议语义变化更新 SnapshotCodec.CurrentVersion |

| 12 | Editor/Tests/Verification/ 与 ProjectVerification.cs | 新能力的实际行为回归加入唯一总入口；保存前后的核心结果、失败回滚和生命周期按影响覆盖 |

## 交付检查

1. 禁用模块必须没有效果；合法配置编译成预期字段；非法配置在编译处给出具体原因。
2. 至少一个隔离世界使用新配置，执行真实触发阶段并检查实际结果。仅检查“编译成功”不能证明消费者已挂接。
3. 有请求时，从 `GameRequestExecution.Execute<T>` 测试成功、权限/阶段拒绝和目标失效，避免只测领域函数而遗漏分派。
4. 涉及资源时验证不足、部分失败和整批回滚；失败不得留下半扣费、半发奖或多余历史。
5. 有持久状态时运行 PersistenceContractVerification，并补精确往返与恢复失败用例；RootState 未登记的新根类型应被拒绝。
6. 涉及表现时检查暂停、退场、读档替换和会话释放；实际素材需要图形 Play 验收。
7. 更新对应制作手册；执行文档检查、相关领域套件及总回归。不要通过改历史迁移基线放行新增内容。

字段覆盖与请求测试能检查已声明的结构约束；“配置是否真的产生设计要求的效果”必须由该能力的行为用例证明，不能靠文件存在或命名检查替代。
