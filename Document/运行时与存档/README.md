# 运行与存档

当前 ECS 快照版本为 **v36**，Easy Save 3 王朝封装为 **v4**。v33/v34/v35 设有字段读取路径，只有通过当前内容指纹校验的旧档才能迁移；调整持久结构或状态语义时更新版本号。

## 当前协议

- `SnapshotCodec` 在地图识别、摘要和完整解码入口统一拒绝非当前版本。
- `SnapshotBinary` 按固定字段顺序显式编码；`ValidateFieldCoverage` 检查登记类型的公开字段，新增字段不能静默遗漏。
- 持久 DTO 只存在于 I/O 边界。个体使用 `Identity.Id`（ulong）。定义引用使用各域 `XxxId`，二进制写入其目录内 `Index`，不是逐条稳定字符串；临时 Entity 引用在保存时清空或恢复时重建。
- 格式与玩法内容签名分别校验。相同格式仍可能因玩法内容改变而无法载入。
- 王朝 v4 由 ES3 序列化为 JSON DTO，外层 Gzip 压缩并校验 SHA-256、格式版本、王朝归属和全部嵌入节点。
- 已移除旧布局读取器、旧格式测试写入器、旧版士兵标记转换、旧账单缺省分支、科技许可转研究记录的补齐逻辑，以及专用于旧协议兼容的测试夹具。

内容签名按目录顺序覆盖 22 种独立 Definition 的稳定 `Metadata.Id` 和玩法字段，并覆盖地图格数据（含边缘区）、原点/尺度/边界、10 个独立 Settings、肖像遗传设置及开局王室、建筑、发放记录。解码先比较签名，因此目录重排或玩法配置变化会拒绝载入，不能把 `XxxId.Index` 跨目录或跨内容版本复用。显示名称、初始人物/建筑名称、默认皮肤、建筑菜单顺序和工作效率 UI 档位不进入玩法签名。任务目标按稳定 `Key` 排序计算签名，`Order` 只控制展示顺序；Key、目标、数量及其他语义不变时，可换序恢复进度。

每夜选择的动态入场区域与波次一同保存、校验和事务恢复，不属于静态内容签名；普通读档不会重新抽选区域。`BuildingDefinition.PlacementAndVisuals.SpawnExclusionPadding` 属于建筑玩法内容签名。

科技完成次数仅保存在 `TechnologyProgress.Completions`，以 `TechnologyId` 引用定义。蓝图、永久 Buff、功能许可、已领任务和完成远征分别保存在 `BlueprintUnlock`、`OwnedBuff`、`UnlockedFeature`、`ClaimedQuest`、`CompletedExpedition`，没有通用许可表或科技许可副本。当前存档的合法性校验、事务回滚、备份和损坏文件保护继续保留。删除旧文件由开发者处理，载入失败不会自动删除玩家文件。

## 状态与存储职责

`Session` 只保留会话阶段和初始化标记。回合/时间由 `GameClock` 保存，随机数由 `SimulationRandomState` 保存；人口、民意、研究点数、远征惩罚、夜晚状态、重试、选择、情报和持久化门禁分别由对应组件拥有，不能重新合并为全量 Session 代理。

`ECS/Persistence/Snapshots` 中的 `BuildingSnapshot`、`SoldierSnapshot`、`HeroSnapshot`、`QuestSnapshot`、`ExpeditionSnapshot`、`PersonSnapshot` 分别定义保存字段和存取过程，共用基类仅含实例身份与变换。`SnapshotCodec` 协调头部、校验与事务；`SnapshotRootStorage` 负责根状态，领域验证器分别验证经济、建筑、研究许可、宫廷、远征与军事关系。不存在 Record.Mask 或跨领域 Definition 字段。

`SnapshotCodec` 是 ECS 权威状态的领域格式，不直接管理磁盘、压缩、备份或存档槽。`RunArchiveCodec` 和 `RunArchiveStore` 是 ES3 边界：前者完成 DTO 序列化与压缩，后者通过 ES3 文件 API 管理主文件、备份、槽位、指针、名称、缩略图、终局墓碑和损坏文件。界面设置使用 ES3 的 PlayerPrefs 后端。

黄昏冻结表分为 `PreparedSoldier`、`PreparedHero`、`PreparedBuildingDefense`；建筑只冻结防御 Profile。运行中的夜晚奖励分为物品、蓝图、Buff 和功能四个 buffer，属于可回滚的暂存结果；存档不保存夜战中途状态，恢复时清除这些暂存表。

## 三类记录

| 记录 | 内容 |
| --- | --- |
| 白天开始节点 | 回合开始、当夜基础计划已锁定的状态 |
| 黄昏节点 | 白天结算与当夜军事准备完成、实时夜晚开始前的状态 |
| 手动存档槽 | 白天当前可操作状态，连同对应的原始节点 |

新王朝、白天开始和黄昏节点自动持久化。手动保存创建独立槽；快速保存覆盖当前手动槽，不替换原始白天/黄昏节点。夜晚不保存逐帧战斗，退出后继续从本夜起点进行；白天未保存的后续操作不会因此自动保存。

文件根为 `Application.persistentDataPath/ECS`，王朝主封装为 `runs/<RunId>/state.lsrun`，最近王朝由 `active-run.txt` 记录。创建新王朝不覆盖其他王朝。

## 共用存档界面与权限

Start 与 Game 打开同一套 UI_SavePanel。视图负责选择和显示，ArchiveApplicationService 负责权限、文件操作与确认失效检查，CheckpointSystem 负责当前 ECS 会话的存取事务。

- Load 模式可跨王朝浏览、载入，并管理独立槽的名称/删除；不能创建或覆盖玩法状态。
- Save 模式显式绑定当前 RunId、存储对象、会话有效性、白天写入能力及执行回调；不能读取或改写其他王朝的槽。夜晚或写入锁定时不得保存、载入或管理槽。
- 自动节点可以选择载入或备份恢复，不能作为独立槽覆盖、重命名或删除。
- 覆盖、删除、改名和载入确认均校验原对象及内容指纹；主封装与备份、独立槽内容改变，即使长度和修改时间相同，旧确认也必须失效。会话结束后旧面板请求失效。

## 终局与回退

PlayerHome 失守触发终局。玩家可回到当回合白天开始或黄昏；同次终局只生成一次恢复票据，新种子更新当夜编成/位置并降低当夜预算。原始回合战力、事件和 Boss 身份保持；下一回合恢复正常预算规则。不显示重试次数、种子或降难比例。

同王朝、同回合的最高已知情报保留到本回合结束，旧已读指纹不能覆盖新报告。回退清除被撤销夜晚的未提交奖励、战报和消息，费用、人口、经验随节点恢复，不保留被撤销战斗收益。

君王必须继承时完全没有在世直系后代则绝嗣。绝嗣不可用夜晚重试绕过，即使没有黄昏节点也能持久保存终局。只有确认“结束王朝”才写入覆灭记录并删除该王朝受管存档，保留历史、不影响其他王朝。

## 事务与文件安全

- ES3 先写 `.tmp` 再提交主文件；覆盖前使用 ES3 生成官方 `.bac` 备份。摘要、版本、归属、地图、内容和全部嵌入节点都要校验。
- 正式文件损坏仅接受同归属备份，后续写入前保留损坏副本。写入失败锁定阶段并提示。
- 删除槽只删除指定王朝/槽的主文件、备份、名称、缩略图和受管损坏副本，不删除自动节点。
- 结束王朝先创建覆灭墓碑，再清理该王朝受管文件；墓碑阻止副本重新载入。未知文件不纳入删除。
- RestoreTransaction 同步执行，保留原实体至候选重建与准备成功，再提交；失败撤销根、Buffer、临时战场和节点归属。根上的 Landsong 类型必须登记为可变捕获或明确只读配置，未登记类型在候选创建前拒绝。候选根不继承待执行请求；取消或发布失败保留原队列与 payload，提交成功才销毁旧请求 payload。
- InventoryTransaction 恢复库存与待存放数组，并将资源账本和追加历史截回事务开始长度。许可、研究点数、事件与可能合并的消息历史由 ProgressionRewardTransaction 另行完整捕获，恢复事务由 RestoreTransaction 记录组件/Buffer 的原先存在性。手动采集、士兵/英雄招募、英雄唤醒和夜晚奖励提交失败不得留下费用、奖励或虚假历史；英雄出场准备还恢复临时战斗、导航与战术组件。

入夜损失清单来自可回滚预演，不是保存点；确认成功才提交白天结算和黄昏节点。GameEvent 自带历史类别，手动库存事务记录命令种类，分类不依赖中文原因文本。

## 持久玩法字段

`BuildingWorkforceState.SubsidyBudget` 保存每回合补贴预算，与已付金额/回合分开；恢复校验预算非负且不超过该级岗位容量，修改未来预算不会抹去已付效果。

PersonRequestEntry 保存远征愿望的创建/解决回合、待安排/在途/完成/拒绝/取消状态和队伍 ID；校验状态、回合、重复待办与队长/在途队伍关系。每人最多 16 条记录，赐婚和个人委托仍读取各自权威状态。Royal 保存性别、登基历史及赐婚请求、请求时君王、回合和冷却字段；主动赐婚候选也是持久人物。

PortraitDNA 保存稳定部件 ID、肤色/发色/眼睛基础 RGB、随机种子、丽质是否已使用和通知状态；SoldierPerson 保存性别、年龄、寿命、换人次数、年龄结算回合、特别关注和死亡通知标记。恢复按类型/性别、必需部件、颜色、年龄、标记与归属校验，不重新随机肖像，也不重新给予捏脸机会。更换相同稳定 ID 的像素素材可以更新表现，删除或改名已被存档使用的部件会使校验失败。DeathNotified 保留以避免重复通知。

Quest 的承接容器 Container/ContainerSlot 与邀约 Source/Slot 分开。进行中和待领奖任务必须满足容器存在、槽号上界与唯一占位；已领奖历史不再绑定容器。分步任务领取后继承原容器、槽号和邀约来源，整条任务链结束才释放；等待额外前置时以 Active、StartTurn=0、Deadline=0 保留原槽。容器失效造成的任务移除与处罚参与事务回滚。

QuestTracking.Mode 为 0 自动选择、1 手动选择、2 明确不追踪，Target 保存目标。自动模式不在定期刷新时重选有效目标，成功领取当前任务后才选择直接后续或最高价值的已接受任务。建筑 Capabilities 编译后的具名记录、初始驻军、任务容量等属于玩法签名；格式版本不代替它们的兼容检查。

## 验证入口

ProjectVerification 统一运行 PersistenceContractVerification 与 ArchiveApplicationServiceVerification，分别输出 `persistence-contract-verification.txt` 和 `archive-application-service-verification.txt`。协议检查包含当前格式精确往返、非当前版本提前拒绝、全部 10 个独立 Settings 的逐字段签名、网格几何及未登记根状态；服务检查覆盖模式权限、跨王朝拒绝、失效会话和过期确认。

领域故障用例使用系统临时目录或 `Library/LandsongEcs/VerificationRuns` 下的独立 GUID 目录，不操作玩家正式文件。测试日志、临时存档与截图是本机可再生结果。实际执行日期与结论见 [验证工作流](../ECS/验证工作流.md) 和 [当前修复与验收记录](../ECS/问题修复记录20260917.md)。
