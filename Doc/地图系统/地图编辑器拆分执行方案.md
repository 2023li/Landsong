# 地图编辑器与主项目拆分执行方案

状态：独立编辑器与自定义地图暂缓；主项目内场景瘦身已落地
基线日期：2026-09-22
首个迁移目标：`Map_Map01`  
Unity 基线：`6000.3.24f1`

## 当前实施范围

2026-09-22 决定暂不建立第二个 Unity 项目，也不承诺自定义地图格式。当前只解决正式地图场景过大：TWC 配置、轻量源场景、MapAsset、逻辑网格和轻量 Entity Scene 继续提交；TWC 生成的运行 Mesh 外置到 Git 忽略的 `Assets/LandsongGenerated/GameMaps`。进入 Play 和 Player Build 前按输入哈希补齐，亦可从菜单清理重建。

该实现是后续拆分方案的低风险前置步骤，不表示跨项目地图包、稳定业务资源目录或移除主项目 TWC 已完成。需要恢复独立地图编辑器工作时，从下文阶段 0/1 的契约与 Golden Report 开始，而不是直接删除当前 TWC 来源。

## 1. 目标

将地图制作和游戏运行拆成两个边界清晰的项目：

```text
地图编辑器项目
TWC 源数据 + 手工地图内容
          │
          │ 导出
          ▼
LandsongMapPackage（跨项目地图包）
          │
          │ 导入、校验、构建前烘焙
          ▼
Landsong 主项目
MapAsset + Mesh + Entity Scene + Addressables/Player 内容
          │
          │ 游戏加载界面异步加载
          ▼
运行时 ECS 世界
```

拆分完成后：

- 地图编辑器项目拥有 TWC、制图场景、地形规则和地图导出工具。
- 主项目不依赖 TWC，不读取制图场景，只读取版本化地图包。
- 主项目的 Mesh、`MapAsset`、Entity Scene 等均为可重建产物，不进入 Git 历史。
- 正式游戏在构建前生成运行时产物；进入地图时加载成品，不在玩家设备执行 TWC。
- 同一地图包重复导入必须产生相同逻辑结果和内容哈希。
- 以后如需随机地图或玩家地图，在同一地图契约上扩展，不重新定义一套地图语义。

## 2. 当前基线与问题

当前地图目录同时保存制图输入和运行输出：

```text
Assets/Landsong/GameMaps/Map_Map01/
├── Map_Map01.unity
└── Map_Map01Data/
    ├── Source/Map_Map01_TWC配置.asset
    └── Generated/
        ├── Map_Map01_烘焙配置.asset
        ├── Map_Map01_逻辑网格.asset
        ├── Map_Map01_Map.asset
        └── Map_Map01_Entities.unity
```

2026-09-21 的实测基线：

| 文件/数据 | 大小或数量 | 性质 |
| --- | ---: | --- |
| `Map_Map01.unity` | 约 156.8 MiB | 制图场景，同时内嵌大量生成 Mesh |
| `Map_Map01_Entities.unity` | 约 120.3 MiB | 运行时生成场景，同时再次内嵌 Mesh |
| `Map_Map01_TWC配置.asset` | 约 10.8 MiB | TWC 实际绘图源数据 |
| 主场景内嵌 Mesh | 1067 个，约 129.2 MiB | 可由 TWC 重建 |
| Entity Scene 内嵌 Mesh | 1037 个，约 117.4 MiB | 与主场景表现高度重复 |
| 初始建筑 | 619 个 | 必须进入地图包并保持身份和摆放 |

单个内嵌 Mesh 的中位数约 13 KiB，90% 分位约 406 KiB，最大约 1.04 MiB。问题不是单个 Mesh 太大，而是大量 Mesh 被重复写入场景，且场景的任意修改都会产生大文件版本。

现有 `GameMapWorkflow`、`TileWorldCreatorMapBaker`、`GameMapPaths` 已经区分了 Source 和 Generated，但两者仍位于同一 Unity 项目，运行输出仍由场景 GUID 和 Unity 对象引用连接。拆分工作要保留现有地图语义与验证，不直接重写玩法地图逻辑。

## 3. 三类资产的所有权

### 3.1 地编源数据 `MapAuthoringSource`

只存在于地图编辑器项目，并进入该项目的版本控制：

- TWC Configuration、Blueprint 绘制数据、Layer 和生成规则；
- 制图场景中的初始建筑、资源点、地图规则区域；
- 额外导航地表和固定通行连接；
- 地图名称、说明、缩略图、边缘宽度、开局参数；
- 地图编辑所需的预览对象和资源目录引用；
- 导出配置和地图稳定 ID。

地编源场景不得保存 TWC 生成的 Mesh、生成瓦片子树或运行时 Entity Scene。编辑器预览生成到本地缓存，关闭项目后允许丢失并重建。

### 3.2 跨项目地图包 `LandsongMapPackage`

它是地图编辑器交付给主项目的唯一正式产物。地图包不包含 Unity Scene，不使用 Unity GUID 表达业务引用，不依赖 TWC 类型。

建议扩展名：`.landsongmap`。第一版可使用固定条目顺序的 ZIP 容器：

```text
Map_Map01.<content-hash>.landsongmap
├── manifest.json
├── gameplay.bin
├── navigation.bin
├── placements.bin
├── presentation.bin
└── thumbnail.png             # 可选
```

其中：

- `manifest.json`：格式版本、地图 ID、显示信息、内容哈希、导出器版本和依赖目录版本。
- `gameplay.bin`：范围、格子、地形、高度、Surface、建造/通行/弹体阻挡和边缘标记。
- `navigation.bin`：额外地表、固定连接、方向、宽度和通行限制。
- `placements.bin`：初始建筑、资源点、旋转、等级、名称和规则区域。
- `presentation.bin`：解析后的瓦片实例或稳定区块几何、材质业务 ID、碰撞用途和包围盒。

首版不要将 TWC Configuration 原样当作地图包。它包含 Unity 子资产和编辑器实现细节，不能成为主项目的长期读取契约。

### 3.3 运行时生成物 `RuntimeMapArtifacts`

只由主项目生成，不进入 Git：

- `MapAsset`；
- `GridMapDefinition`（如果过渡期仍需要）；
- 外置 Mesh `.asset`；
- Entity Scene/SubScene；
- Addressables 或其他平台构建内容；
- 导入报告、内容哈希和局部缓存。

建议统一生成到：

```text
Assets/LandsongGenerated/GameMaps/<map-id>/
```

并将整个 `Assets/LandsongGenerated/` 加入 `.gitignore`。生成器必须能在干净检出、开发机和 CI 中创建这个目录。

## 4. 共享地图契约

建立共享 UPM 包 `com.landsong.map-contract`，地图编辑器项目和主项目引用同一版本。第一阶段可先放在主仓库中开发；接口稳定后迁移到独立仓库，以 Git URL 或内部包源引用。

目标结构：

```text
Packages/com.landsong.map-contract/
├── package.json
├── Runtime/
│   ├── Format/
│   ├── Serialization/
│   ├── Validation/
│   └── Hashing/
└── Tests/
    └── Runtime/
```

共享包可以依赖 Unity Runtime 类型或纯 .NET，但不得引用：

- `UnityEditor`；
- TWC 程序集；
- 主项目 ECS Authoring 类型；
- 地图编辑器窗口或场景组件；
- `AssetDatabase`、`SceneAsset`、`SubScene`。

### 4.1 第一版必须覆盖的数据

当前 `MapAsset`、`GridMapDefinition` 和 `MapContentAuthoring` 中影响运行结果的数据必须全部有对应字段：

| 分类 | 第一版字段 |
| --- | --- |
| 身份 | `MapId`、格式版本、内容版本、内容哈希 |
| 范围 | `Min`、`Size`、`Origin`、`CellSize`、`ElevationStep`、边缘宽度 |
| 格子 | Exists、Buildable、Traversable、BlocksProjectile、Elevation、Surface、Height、Terrain |
| 导航 | NavigationSurfaces、AuthoredConnections 及其方向/宽度/层级 |
| 初始内容 | 建筑稳定 ID、名称、Cell、Level、Rotation |
| 开局 | DynastyName、BasePopulation、Seed |
| 菜单 | DisplayName、Description、Thumbnail 标识 |
| 表现 | 区块 ID、位置、旋转、缩放、Mesh/瓦片数据、Material ID、Collider 用途 |

### 4.2 稳定 ID

跨项目引用一律使用稳定业务 ID，不使用 Unity GUID、资源路径或数组索引。例如：

```text
terrain.land
terrain.mud
terrain.water
tile.land.green.center
tile.ramp.green.south
material.terrain.green
building.palace
resource.iron.small
```

主项目维护 `StableId -> Runtime Asset/Definition` 映射。地图编辑器消费只读的地图制作目录，目录至少包含显示名称、稳定 ID、占地、允许地形和预览资源。玩法定义仍由主项目拥有；地图编辑器不得复制并独立维护另一份规则真相。

### 4.3 确定性与哈希

地图包必须使用规范化顺序：

- 格子按 `Surface/Elevation/Z/X` 排序；
- 初始对象按稳定类型 ID、Cell、Rotation、稳定实例 ID 排序；
- 连接按 Surface 和端点排序；
- 表现区块使用 `Layer/ChunkX/ChunkY` 稳定命名；
- 字典在写入前转为排序数组；
- 内容哈希不包含导出时间、绝对路径和机器信息；
- 所有浮点必须有限，关键坐标按契约规定精度量化或按 IEEE 位模式写入；
- ZIP 条目顺序和压缩参数固定。

相同输入连续导出两次，应得到相同 `contentHash`。文件字节完全一致作为目标；如果 ZIP 元数据暂时妨碍字节一致，至少解包后的规范化内容必须一致。

### 4.4 格式版本

`manifest.json` 至少包含：

```json
{
  "magic": "LANDSONG_MAP",
  "schemaVersion": 1,
  "mapId": "Map_Map01",
  "contentHash": "...",
  "catalogVersion": "...",
  "exporterVersion": "..."
}
```

首版只要求读取当前 `schemaVersion`。格式变化时提升版本并重新导出官方地图。以后开放玩家地图前，再确定兼容窗口和迁移策略。

## 5. 主项目执行方案

### 5.1 过渡期职责

在完成 Map01 对照验收之前，保留现有 `GameMapWorkflow` 作为 Legacy 路径，并新增 Package 路径。两条路径不得同时写同一输出目录。

建议增加：

```text
Assets/Landsong/Scripts/MapRuntime/
├── LandsongMapPackageReader.cs
├── LandsongMapValidator.cs
├── RuntimeMapCompiler.cs
├── RuntimeMapCatalog.cs
└── StableMapContentResolver.cs

Assets/Landsong/Scripts/Editor/MapImport/
├── LandsongMapImporter.cs
├── RuntimeMapArtifactWriter.cs
├── RuntimeMapBuildPreprocessor.cs
└── RuntimeMapImportCommandLine.cs
```

名称可以调整，职责不能重新混回一个类。

### 5.2 导入流程

主项目导入一张地图时按以下顺序执行：

1. 读取 `manifest.json`，验证 magic、schema、地图 ID 和内容哈希。
2. 检查所有稳定资源 ID 是否存在于主项目目录。
3. 对尺寸、数量、坐标、浮点值、连接、建筑占地和边缘通路执行完整校验。
4. 在临时输出目录生成候选 `MapAsset`、外置 Mesh 和 Entity Scene。
5. 使用现有 `GameWorldMapAuthoring.BuildGrid`、导航编译和地图校验验证候选。
6. 校验成功后原子替换 `Assets/LandsongGenerated/GameMaps/<map-id>/`。
7. 更新生成的运行地图目录和 Game 宿主引用。
8. 写入 `import-report.json`，记录输入哈希、输出摘要和工具版本。
9. 任一步失败都保留上一份有效运行输出。

当前 `GameMapWorkflow.OutputTransaction` 的失败回滚原则继续保留，但目标改为候选目录整体提交，减少逐文件恢复复杂度。

### 5.3 Mesh 与表现

第一版采用“地图编辑器导出稳定表现区块，主项目生成 Unity Mesh 资产”：

- 区块 ID 使用 `Layer/ChunkX/ChunkY`，不使用连续编号；
- 主项目生成同路径 Mesh 并保持 `.meta` 稳定；
- Entity Scene 和编辑器预览共同引用外置 Mesh，不再各自内嵌一份；
- 未变化区块的规范数据和生成 Mesh 保持不变；
- 材质由业务 ID 在主项目解析，地图包不保存 Unity 对象引用；
- 碰撞 Mesh 明确标记，不从对象名称推断。

如果第一版直接导出解析后的瓦片实例而非几何，主项目必须拥有与编辑器一致的瓦片资源和确定性合并器。两种表现编码只能选择一种作为 v1，不能同时留下两套无权威关系的输出。

### 5.4 构建与本地运行

新增统一命令：

```text
ImportOfficialMaps
VerifyOfficialMaps
BuildPlayerWithMaps
```

实际实现可使用 Unity 命令行静态入口。构建前处理器必须：

1. 读取官方地图发布清单；
2. 检查本地地图包是否存在且哈希匹配；
3. 缺失时给出明确错误，CI 可在前序步骤下载；
4. 导入所有变化的地图；
5. 验证生成场景和地图菜单；
6. 之后才允许 Player Build。

本地进入 Play Mode 时不应静默执行分钟级全量导入。地图包过期时显示明确状态，由开发者执行导入；开发构建可以提供“缺失时导入”的显式按钮或命令。

### 5.5 运行时加载

正式游戏保持当前“加载界面选择并加载地图子场景”的行为。运行时只做：

- 根据 `MapId` 选择已构建地图；
- 异步加载 Entity Scene/Addressables；
- 校验运行时地图身份；
- 初始化 ECS Session；
- 失败时返回菜单并显示可诊断错误。

正式发行版本不包含 TWC，不在玩家设备合并 Mesh，也不调用编辑器地图烘焙代码。

### 5.6 主项目最终保留与移除

最终保留：

- `com.landsong.map-contract`；
- 地图包读取、校验、稳定 ID 解析；
- 构建前运行时产物生成器；
- ECS 地图编译和加载；
- 官方地图发布清单；
- 地图契约和回归测试。

Map01 迁移验收完成后移除：

- 主项目中的 TWC 插件及其编辑 UI；
- 正式地图 TWC Configuration；
- 正式地图制图场景；
- 旧 `Generated` 目录中的已提交运行输出；
- 只为 TWC 制图存在的主项目 Editor 代码。

实验地图 `Map_TWCFlowLab` 和 `Map_NavigationLab` 的去留单独决定，不能在 Map01 迁移中顺手删除。若仍作为主项目技术验证使用，应改为测试项目或测试夹具；若属于 TWC 验证，应迁入地图编辑器项目。

## 6. 地图编辑器项目执行方案

### 6.1 项目建立

新建独立 Unity 项目和仓库，暂定名称 `LandsongMapEditor`。首轮迁移使用与主项目相同的 Unity `6000.3.5f2`，降低序列化和渲染差异。

地图编辑器项目包含：

- TWC 及所需编辑扩展；
- `com.landsong.map-contract`；
- 地图制作所需的瓦片、材质、建筑预览和规则目录；
- 制图场景与 TWC 源配置；
- 地图校验、预览、导出和发布工具；
- 地图导出回归测试。

地图编辑器项目不包含完整 ECS 模拟、存档、战斗、UI 和游戏运行场景。

### 6.2 建议目录

```text
Assets/LandsongMapEditor/
├── Editor/
│   ├── Export/
│   ├── Validation/
│   └── Publishing/
├── RuntimePreview/
├── Catalogs/
└── MapSources/
    └── Map_Map01/
        ├── Map_Map01.unity
        └── Source/
            └── Map_Map01_TWC配置.asset

Library/LandsongMapEditor/
├── PreviewCache/
└── ExportStaging/

Exports/                         # Git 忽略，本地发布暂存
└── Map_Map01/
```

`MapSources` 只保存人工成果；TWC 生成对象和合并 Mesh 放入 `Library` 缓存。打开场景时：

- 输入哈希匹配则加载/恢复本地预览缓存；
- 缓存缺失或过期则运行 TWC 生成；
- 保存场景前清除或剥离可重建生成对象；
- 关闭后删除缓存不影响地图源数据。

### 6.3 地图制作目录

玩法规则由主项目拥有，地图编辑器消费一份机器生成的只读目录，例如：

```text
MapAuthoringCatalog
├── catalogVersion
├── terrains
├── buildings
├── resources
├── materials
└── tiles
```

主项目发布目录快照时包含稳定 ID、显示名称、占地、旋转规则、允许地形、预览资源标识等制图所需字段。地图编辑器不得手工修改这些玩法字段；版本不匹配时禁止发布地图。

瓦片 Mesh、材质和预览 Prefab 可以放在独立共享美术 UPM 包中，由两个项目引用。若暂时无法拆美术包，首版允许复制到编辑器仓库，但必须以稳定 ID 校验，不能依赖两个项目恰好拥有相同 GUID。

### 6.4 导出流程

“发布地图”执行以下步骤：

1. 保存制图源场景和所有 TWC 子资产。
2. 锁定本次导出使用的契约、目录和 TWC 版本。
3. 使用固定种子从头生成 TWC 地图。
4. 解析 Layer/Blueprint 得到逻辑格。
5. 收集额外地表、固定连接、初始建筑和规则区域。
6. 将 Unity 对象引用解析为稳定业务 ID。
7. 将生成表现转换为稳定区块记录。
8. 执行地图范围、地形唯一性、连接、占地、核心建筑和边缘通路校验。
9. 规范化排序并计算内容哈希。
10. 写入临时地图包，重新读取并再次校验。
11. 原子移动到 `Exports/<map-id>/`。
12. 生成便于人工检查的导出报告。

任何失败都不得覆盖上一份已发布地图包。

### 6.5 发布方式

不要用 Git LFS 长期保存每一次 `.landsongmap` 草稿。推荐区分：

- 地编仓库：保存 TWC 源数据和小型配置；现有模型、贴图等二进制源资源按类型使用 LFS。
- 本地导出：保存到 Git 忽略的 `Exports/`。
- 正式地图包：上传到版本化制品存储，以 `mapId/contentHash` 标识，不覆盖旧版本。
- 主项目：只提交小型官方地图清单，CI 和开发工具按清单获取地图包。

制品存储可以后续选择对象存储或发布制品服务。第一阶段先实现本地文件提供器，读取接口不得绑定具体服务。

## 7. 分阶段迁移

### 阶段 0：冻结基线

不改运行流程，只记录现有 Map01：

- MapAsset 内容哈希；
- 格子数、范围、地形分布和高度分布；
- NavigationSurface 和 Connection 数量及内容；
- 619 个初始建筑的稳定定义、格子、等级和旋转；
- 边缘可通行入口；
- Mesh 数量、Bounds、材质和碰撞用途；
- 游戏地图加载、重复进入和释放结果；
- 一组固定视角截图。

输出为机器可比较的 Golden Report，不依赖 156 MiB 场景文本本身作比较。

完成条件：基线报告可以在现有 Legacy 烘焙后重复生成并通过。

### 阶段 1：在主仓库建立契约和往返闭环

此阶段尚不拆项目：

1. 创建共享地图契约 v1。
2. 从现有 `MapContentAuthoring + TWC` 导出 `.landsongmap`。
3. 在临时目录重新读取地图包并生成候选运行数据。
4. 对候选运行数据执行 Golden Report 对比。
5. Legacy 和 Package 两条路径并存。

完成条件：Map01 导出后重新导入，逻辑数据、导航、初始建筑和表现摘要全部一致；连续两次导出内容哈希一致。

### 阶段 2：生成物退出 Git

1. 外置并稳定命名 Mesh。
2. 将运行输出迁入 `Assets/LandsongGenerated/GameMaps`。
3. 建立 `.gitignore` 规则和构建前导入入口。
4. 让 Game 地图目录和 SubScene 引用由生成器维护。
5. 在干净检出环境运行地图导入、测试和 Player Build。

完成条件：删除整个 `Assets/LandsongGenerated` 后，可以从地图包重新生成并成功构建、进入 Map01。主项目不再需要提交超过 100 MiB 的地图场景。

### 阶段 3：建立独立地图编辑器项目

1. 创建 `LandsongMapEditor`。
2. 接入相同契约包和只读制图目录。
3. 复制 Map01 制图源；先不删除主项目原件。
4. 在新项目生成并导出 Map01。
5. 主项目导入新项目产物并完成全部对照验收。
6. 连续一个发布周期只使用新项目编辑 Map01。

完成条件：地图修改只在编辑器项目进行；主项目仅通过地图包接收变化；两个项目的 CI 都能独立完成各自验证。

### 阶段 4：切换并清理 Legacy

满足阶段 3 后：

1. 将主项目正式地图 TWC 来源标为只读归档。
2. 删除主项目正式制图场景和 TWC 配置。
3. 删除 Legacy 地图烘焙入口及只被它使用的代码。
4. 移除主项目 TWC 依赖。
5. 更新地图制作、构建、发布和故障恢复文档。
6. 单独处理 Git 历史中的超限文件；不要把历史重写混入功能迁移提交。

完成条件：主项目全量编译、验证和构建均不包含 TWC；地图编辑器仓库不包含主项目玩法运行代码。

### 阶段 5：可选的随机地图和玩家地图

这一阶段不属于当前大文件修复的完成条件。

- 随机地图：在受控输入和 Seed 下生成同一 `MapDocument`，再进入公共校验/编译链。
- 玩家地图：增加运行时包读取、资源白名单、数据上限和兼容策略。
- 玩家地图不得携带程序集、Shader、任意资源路径或可执行内容。
- 如果运行时生成 Mesh，需要单独进行目标平台性能和内存验收。

## 8. 验收矩阵

### 8.1 数据一致性

- `MapId`、尺寸、原点、格尺寸和高度单位一致。
- 每个 Cell 的全部运行字段逐项一致。
- 所有额外地表和固定连接一致。
- 619 个初始建筑的定义、位置、等级、旋转和名称一致。
- 地图菜单显示信息和缩略图一致。
- 相同输入重复导入的运行内容哈希一致。

### 8.2 表现与碰撞

- 区块 Bounds、顶点/索引摘要、SubMesh 和 Material ID 一致。
- 主场景与 Entity Scene 不再分别内嵌重复 Mesh。
- 坡道、桥梁、桥下地面及多高度表面表现正确。
- 碰撞来源明确且重开、构建后仍有效。
- 固定视角截图不存在可见缺块或材质丢失。

### 8.3 玩法与加载

- Map01 能从菜单进入、退出并重复进入。
- ECS 只生成一个地图根，地图身份正确。
- 初始建筑、占地和核心建筑规则通过。
- 边缘存在可达入场通路。
- 建造、寻路、夜间入场和存档地图身份验证通过。
- 地图加载失败不会留下半初始化 World。

### 8.4 构建与仓库

- 干净检出不包含生成地图产物也能完成地图导入。
- CI 在地图包缺失、哈希不符或目录版本不符时明确失败。
- Windows 目标构建通过；后续目标平台逐一验证。
- 主项目没有单个正式地图文件超过 GitHub 100 MiB。
- 修改一个局部区块时，导入报告只标记受影响区块变化。

## 9. Git 与制品策略

主项目 Git 提交：

- 地图契约版本引用；
- 读取、校验、构建和加载代码；
- 稳定 ID 目录源；
- 官方地图发布清单；
- 测试和文档。

主项目 Git 忽略：

- `Assets/LandsongGenerated/`；
- 地图包下载缓存；
- 地图导入报告和临时目录。

地图编辑器 Git 提交：

- TWC 源配置；
- 小型制图源场景；
- 手工地图内容；
- 导出器和验证器；
- 地编专用配置。

地图编辑器 Git 忽略：

- TWC 生成预览 Mesh；
- 导出暂存；
- 已发布地图包本地缓存。

模型、贴图、音频等不可有效文本差分的源资源继续使用 LFS。不要把整个 `*.asset` 或 `*.unity` 纳入 LFS；如过渡期必须提交生成 Mesh，只对明确的生成 Mesh 目录配置 LFS，并在阶段 2 完成后取消该过渡方案。

## 10. 回滚和风险控制

### 10.1 回滚原则

- 阶段 1 到阶段 3 始终保留 Legacy Map01 和上一份有效地图包。
- Package 导入失败时继续使用上一份有效生成目录。
- 未通过 Golden Report 不切换游戏菜单和 SubScene 引用。
- 主项目移除 TWC 是最后一步，不与格式设计、导入器首版放在同一个变更中。
- 旧大文件的 Git 历史清理在功能稳定后单独执行，并提前通知所有协作者重新同步仓库。

### 10.2 主要风险

| 风险 | 控制措施 |
| --- | --- |
| 两项目资源 ID 漂移 | 主项目生成只读目录；导出和导入同时校验 `catalogVersion` |
| TWC 输出不确定 | 固定种子、排序和版本；连续导出哈希测试 |
| Unity GUID 跨项目失效 | 地图包只使用稳定业务 ID |
| Mesh 表现不一致 | 导出稳定区块数据；比较 Bounds、几何摘要、材质 ID 和截图 |
| 构建机缺地图包 | 发布清单固定内容哈希；构建前显式获取并校验 |
| 导入失败破坏可用地图 | 候选目录生成，成功后原子替换 |
| 契约过早承诺玩家兼容 | v1 仅承诺当前官方地图；玩家地图另立兼容策略 |
| 拆分期间同时编辑两份 Map01 | 阶段 3 明确唯一写入项目，另一份只读 |

## 11. 建议的变更批次

按以下批次提交，任何批次失败都不应阻止 Legacy 地图继续工作：

1. **地图基线**：Golden Report 和现有 Map01 回归入口。
2. **契约 v1**：共享 DTO、序列化、校验和哈希。
3. **Legacy 导出器**：从当前 TWC/MapContentAuthoring 导出地图包。
4. **主项目导入器**：地图包生成候选 `MapAsset` 和运行目录。
5. **表现区块**：外置 Mesh、稳定区块 ID、去除场景重复内嵌。
6. **构建集成**：命令行导入、发布清单、干净检出构建。
7. **编辑器项目**：新仓库、TWC 源迁移、目录和发布工具。
8. **Map01 切换**：新项目导出成为唯一来源，观察一个发布周期。
9. **Legacy 清理**：主项目删除正式 TWC 制图依赖和旧生成输出。
10. **历史治理**：按团队协作窗口处理尚未推送或远端 Git/LFS 历史。

## 12. 后续拆分方向（当前暂缓）

若重新启动独立地图编辑器，本方案保留以下方向：

- 地图编辑器可最终作为独立 Unity 项目。
- 完成 Map01 跨项目对照后，主项目才可移除 TWC。
- 官方地图采用“编辑器导出、主项目构建前烘焙、运行时加载成品”。
- 地图包使用稳定业务 ID，不使用跨项目 Unity GUID。
- 运行时生成和玩家地图属于后续能力，不阻塞当前拆分。
- 先在当前仓库验证契约和往返闭环，再移动源数据。
- Map01 是首个也是切换前唯一必须完成全量对照的正式地图。

当前不执行跨项目迁移、自定义地图或玩家地图；也不删除主项目中的 TWC 源。
